# План: перенести синхронізацію товарів LP-CRM з браузера на сервер

## Навіщо

Зараз щоденна синхронізація товарів LP-CRM (`talvyna-crm-price-sync`, Cowork-задача,
09:09 щодня) виконується через **Claude in Chrome**: скрипт заходить у відкриту вкладку
залогіненого браузера і виконує JS-запити з контексту сторінки. Це працює, але має
проблеми:
- Задача зупиняється, якщо сесія браузера розлогинилась (трапляється часто — бачили це
  сьогодні кілька разів).
- Залежить від відкритого Cowork-сеансу з підключеним Chrome.
- Немає гарантованої доставки звіту (звіт лишається тільки в чаті Cowork).

Мета: перенести цю ж логіку в **serverless-функцію на Vercel** (той самий стек, що
`api/order.js`, `api/img-usage-check.js`), яка виконується по cron-розкладу і не залежить
від браузера чи відкритого чату.

## Що встановлено сьогодні (важливо для реалізації)

### 1. У LP-CRM НЕМАЄ публічного API для запису товарів
Є лише `POST /api/addNewOrder.html` (створення замовлень, ключ `LPCRM_KEY`, вже
використовується у `api/lpcrm.js`). Для товарів такого API немає — тільки внутрішні
ендпоінти, якими користується сама вебка на `rosydial.lp-crm.biz`, авторизовані
сесійною кукою.

### 2. Логін — просте `GET`, без CAPTCHA і CSRF-токена
Форма логіну (`https://rosydial.lp-crm.biz/login`):
```html
<form method="get" action="https://rosydial.lp-crm.biz/login">
  <input name="login" type="text">
  <input name="pass" type="password">
  <input name="REQUEST_URI" type="hidden">
  <input name="HTTP_REFERER" type="hidden">
</form>
```
Тобто теоретично можна залогінитись звичайним `fetch()` (GET-запит з `login`/`pass` у
query-string) і забрати сесійну куку з заголовка `Set-Cookie` відповіді — без headless-
браузера. **Це треба перевірити руками** (запустити такий запит і подивитись, чи справді
повертається робоча кука, чи є прихований захист типу rate-limit/fingerprint-перевірки).

⚠️ Логін через GET з паролем у query-string — це особливість самого LP-CRM, не наш вибір.
Не логувати повний URL запиту (з паролем) ніде в консоль/Sentry.

### 3. Читання і запис картки товару — вже відомі ендпоінти
Використовуються сьогоднішнім браузерним скриптом, повністю робочі:
- Прочитати поточні значення полів картки:
  `POST /include/modal_products.php?id={id}` (заголовок `X-Requested-With: XMLHttpRequest`)
  → повертає HTML-форму, з якої треба витягнути значення всіх `input/select/textarea`.
- Записати зміни:
  `POST /ajax_products` з `FormData`, що містить **усі** поля форми (не тільки змінені!)
  плюс `action=update` (або `action=insert` для нової картки) — сервер LP-CRM, схоже,
  очікує повний стан форми, а не патч.
- Поле собівартості: `price_enter`. Поле ціни продажу: `price`. Категорія:
  `category_id` (5 = Купальники, 6 = Пляжні накидки).

### 4. Список товарів і пагінація — НЕ перевірено
Браузерний скрипт гортає сторінки списку через клієнтську функцію `Navigation('2')`,
`Navigation('3')` тощо — це JS-функція, вбудована в сторінку `/products`, і незрозуміло,
чи робить вона просто AJAX-запит на якийсь URL (який можна викликати напряму), чи щось
складніше. **Перед реалізацією обов'язково подивитись у DevTools → Network, що саме
викликає `Navigation()`**, і використати той самий ендпоінт напряму.

## Пропонована архітектура

```
Vercel Cron (vercel.json, напр. "0 9 * * *")
  → GET /api/cron/crm-sync
      1. Логін у LP-CRM (GET /login?login=...&pass=...), зберегти Set-Cookie
      2. Зібрати список товарів CRM (id + артикул) — ендпоінт з п.4 вище
      3. Взяти джерело істини (див. нижче), порівняти price / price_enter
      4. Для розбіжностей — POST /ajax_products (з тією ж кукою)
      5. Надіслати звіт у Telegram (TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID — вже є в env)
```

### Джерело істини для цін і собівартості

Зараз ціна продажу береться з Supabase (`products.price`), а собівартість — з окремої
Google-таблиці «Вибір товарів» (яку навіть Claude не зміг стабільно читати по вкладках
через Drive-конектор). Рекомендація: **додати колонку `cost_price` у таблицю
`products` у Supabase** і заповнити її один раз вручну (дані вже є — 63 SKU, я їх сьогодні
заносив у CRM, ті самі значення). Тоді сервер:
- Читає і ціну, і собівартість з одного джерела (Supabase, уже є `SUPABASE_URL`/
  `SUPABASE_ANON_KEY` в `config.js` і `.supabase-service-key` для запису).
- Не залежить від Google Sheets API / OAuth взагалі.

Якщо не хочете заводити нову колонку в Supabase — альтернатива: тримати статичний
JSON-файл `api/cost-prices.json` у репозиторії (артикул → собівартість), оновлювати
вручну при зміні прайсу постачальника. Простіше, але вимагає деплою при кожній зміні
цін постачальника.

### Змінні оточення (додати у Vercel)
```
LPCRM_LOGIN     — логін LP-CRM (окремо від LPCRM_KEY, який для API замовлень)
LPCRM_PASSWORD  — пароль LP-CRM
```
Тримати в секреті, не комітити.

### Розсилка звіту
Використати вже готовий патерн з `api/img-usage-check.js` — `fetch` на
`https://api.telegram.org/bot${TOKEN}/sendMessage` з `TELEGRAM_BOT_TOKEN`/
`TELEGRAM_CHAT_ID` (ті самі, що для сповіщень про замовлення).

## Кроки реалізації

1. У Chrome DevTools подивитись, який запит робить `Navigation()` на сторінці
   `/products` — записати URL/метод/параметри.
2. Написати і вручну протестувати логін-запит (крок 2 вище) окремим скриптом — 
   підтвердити, що кука дійсно авторизує наступні запити.
3. Додати колонку `cost_price` в Supabase (або статичний JSON, якщо простіше).
4. Створити `api/cron/crm-sync.js` за архітектурою вище. Спочатку — **dry-run режим**
   (`?dry=1`): рахує розбіжності, шле звіт у Telegram, нічого не пише в CRM. Звірити
   результат dry-run з тим, що зараз в CRM (я сьогодні вручну звірив і заповнив 63
   картки — розбіжностей бути не повинно).
5. Тільки після успішного dry-run — увімкнути реальний запис.
6. Додати `{ "path": "/api/cron/crm-sync", "schedule": "0 9 * * *" }` у `vercel.json`
   поруч з існуючим cron.
7. Вимкнути (або лишити як резервний ручний запуск) Cowork-задачу
   `talvyna-crm-price-sync`, коли серверна версія стабільно попрацює кілька днів.

## Ризики

- Якщо LP-CRM змінить логін-механізм (додасть CAPTCHA/2FA) — серверний варіант
  зламається без попередження. Cron має **гучно** сповіщати в Telegram про будь-яку
  помилку (не «тиха» відмова), щоб це було одразу помітно.
- `/ajax_products` вимагає повний набір полів форми — якщо LP-CRM додасть нове
  обов'язкове поле, запис може почати падати. Тримати той самий підхід «прочитати
  форму → підмінити 1-2 поля → відправити все» (як зараз), а не збирати FormData
  вручну з нуля.
